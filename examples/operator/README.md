# Operator request examples

These files are templates. Replace the uppercase address, timestamp and amount placeholders and the RPC URL before use. None of them contain keys. The [Guide](../../docs/site/index.html#participants) explains who can act.

- `deployment.json`: read-only `prepare-deployment` input. Save its output as `deployment-plan.json`. It predicts eight deployments: the two linked libraries first, then the vault implementation, Hub, modules and indicative feed. The result is physical-only, with `cashSettlementEnabled` false and no publisher. Supply explicit `expiryPricePublicationWindow` and `exerciseWindow` values in seconds. The 3,600-second values in the example are illustrative, not production defaults. A `settlementMethodology` reference may be stored in the plan as metadata but is not required.
- `deployment-run.json`: explicit deployment or resume input. Keep its journal between attempts.
- `registry-deployment.json`: `prepare-registry-deployment` input for the separate release registry. Save the result as `registry-plan.json`. It does not touch the eight-contract Hub sequence.
- `registry-resume.json`: `deploy-registry` input naming that plan and its own recovery journal. Execution needs `--send`.
- `release-bundle.json`: `prepare-release-bundle` input naming a completed Hub plan and journal. Run it from that release's matching build and save the verified output as `release-1.json`.
- `registry-register.json`: `register-version` input naming the registry, release ID and saved bundle. Simulation verifies the deployment evidence and binds the bundle hash; submission needs `--send`.
- `registry-recommend.json`: `recommend-version` input. It selects an already registered release and does nothing to any Hub.
- `registry-claim.json`: `claim` through an explicitly selected registry release, with the position's local vault ID and share amount. The transaction still goes to the original Hub whatever the current recommendation.
- `vault.json`: private physical covered-call preparation, 10 WETH, 20% out of the money, with an illustrative $10,000 minimum. Review the token and price inputs for your chain.
- `cash-vault.json`: cash covered-call preparation for use after the publisher grant and feature activation. It carries the required methodology reference and a positive observation age.
- `bid.json`: `typed-bid` input. Copy its complete output `value` into an activation request's `bid` and collect the buyer signature. `activation.json` shows the envelope.
- `spot-report.json`: `IvyPriceFeed` `typed-report` input for activation checks. Add `signature` to relay it with `publish-spot`. Cash settlement uses the Hub publication requests below.
- `settlement-exercise.json`: `publish-settlement-exercise` input for a direct publisher transaction to `hub`. Its `validUntil` is enforced at exercise, alongside the vault's maximum observation age.
- `settlement-expiry.json`: `publish-settlement-expiry` input for the historical calculation at the exact expiry. Publication is irreversible and must land strictly before expiry plus the vault's saved expiry price publication window, as well as no later than the report's `validUntil`.
- `settlement-status.json`: read-only `inspect-settlement` input. Output includes the original settlement type, effective route, publication and fallback deadlines, and permissionless expiration availability. The labeled `physicalExercisePreview` shows whether physical exercise is currently available plus the payment token, amount, clone spender, wallet balance and allowance. An unavailable preview is not a cash exercise funding requirement. Add an optional `amount` to preview a partial exercise; otherwise it uses all remaining notional.
- `exercise-fallback.json`: explicit `exercise-fallback` input, calling `exercisePhysicalFallback`. Approve its previewed payment token to the clone first: calls require quote at the strike (rounded up), puts require underlying. Only the buyer or authorized executor may submit, with delivery to the configured recipient. Ordinary `exercise` never silently switches to physical delivery.
- `settlement-role.json`: `grant-settlement-publisher` or `revoke-settlement-publisher` input, sent by the Hub admin. Role changes decide who may publish and never toggle cash availability.
- `cash-feature.json`: `set-cash-settlement-enabled` input. To enable, nominate an already authorized publisher for the CLI preflight; the transaction carries only the boolean. To disable during an outage, set `enabled: false` with no publisher.
- `transaction.json`: the common envelope. Add `amount` for deposit, withdraw, exercise and claim. Expire, claim-premium and claim-payout take no amount.
- `unwind-proposal.json`: first run `typed-unwind-proposal` with vaultId, deadline and refund to preview the next agreement. Have the buyer sign its typed data, then submit `propose-unwind` as owner or buyer with `buyerSignature`. Both callers need the signature. Collect each holder's `approve-unwind` with the previewed nonce; `typed-unwind` can inspect the stored agreement. A replacement needs a fresh buyer signature, and a stale signature reverts without clearing existing approvals or funding. `unwind-funding.json` is an LP's `fund-unwind` request after approving the clone for premium tokens; every current LP owes its proportional rounded-up contribution regardless of premium already claimed. `unwind-execution.json` supplies the same buyer signature as `signature` once consent and funding are complete; anyone can execute without providing tokens. `unwind-recovery.json` with `withdraw-unwind-contribution` recovers a deposit from a failed proposal or the excess after execution. The [Guide](../../docs/site/index.html#early-exit) explains consent, funding and recovery.

Capture JSON to disk with `node scripts/operator.mjs <command> file.json > prepared.json`. `npm run operator -- ...` also works, but npm prints a banner into stdout. Nothing is submitted unless you add `--send`.

The [release and integration guide](../../docs/site/releases.html) has the full registry workflow. For everyday operations, either add `registry`, `releaseId` and `releaseBundleFile` or keep an explicit `hub`; if both are present they must agree. Only `prepare-vault` may omit `releaseId` and take the recommendation. An existing position always keeps its original Hub and local vault ID, and because every CLI run prepares afresh, pin the release ID when repeating a request. This tooling supports bundle format 1, the `ivy-vaults-v4` interface and Hub manifest format 7. Historical releases, including `ivy-vaults-v2`/manifest 6, require their preserved operator build and artifacts. Existing suites do not acquire fallback through registration or recommendation.

`terms.allowPartialExercise` must be set explicitly in `vault.json`. False requires full exercise, true permits partial exercise, and the choice is locked before the first deposit.

To opt into cash, the Hub admin first prepares and submits `grant-settlement-publisher` with `settlement-role.json`, naming an EOA or an existing authenticated helper, then `set-cash-settlement-enabled` with `cash-feature.json`. Check `cashSettlementEnabled()` before using `cash-vault.json`. A cash vault needs a positive `terms.maxSettlementPriceAge`, fixed at creation, and a `settlementMethodology` reference. An optional `spotBand` block adds a SpotBand rule checked at activation against the indicative feed; a signed spot report there cannot stand in for a missing authoritative report. `bidRules` names the release's shipped validator and may be omitted when a registry release is resolved. Before production cash admission, the referenced methodology must specify each pair's source, sampling, weighting, rounding, missing-sample and outage handling, observation validity, expiry calculation, responsible operator and evidence location. The tooling stores the reference and attests nothing about the source.

Cash-capable creation previews and cash bid previews disclose `P = expiryPricePublicationWindow`, `W = exerciseWindow`, `D = expiry + P` and `F = D + W`. Creation snapshots both settings; verify the mined vault's saved terms before deposits. A cash bid binds those immutable terms through its signed vault identity. Bid fields and the EIP-712 domain version remain unchanged; the new Hub address keeps signatures tied to the new deployment.

If no final price arrives before `D`, both American and European cash options offer explicit physical exercise over `D <= now < F`. At `F`, anyone can run `expire` even if the buyer does nothing and no fallback transaction occurred. LPs then use `claim`; the unexercised remainder lapses without creating a cash reserve. Timely final prices stay valid after both deadlines and never enter fallback. Early American cash exercise still needs a valid exercise observation.

`test/17-local-rehearsal.test.ts` rehearses deployment, original physical delivery, cash admission, timely publisher replacement, cash claims, fallback payment previews, explicit physical exercise and permissionless LP recovery on first interaction after the fallback deadline. Run it with `npx hardhat test test/17-local-rehearsal.test.ts`. Rotate a failed publisher and publish the verified historical expiry price only before `D`. After `D`, inspect the route, fund and approve physical delivery if the buyer chooses to exercise before `F`, or expire at/after `F` and claim LP assets. Admission pauses and cash-admission disabling do not suspend those deadlines or recovery. Each publication still targets one Live cash vault by `vaultId`, even when another vault shares its pair and expiry.
