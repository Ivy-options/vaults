Release registry specification

Objective

One permanent discovery address per chain lets future Hub releases coexist with existing vaults. Every deployed Hub, vault implementation and module keeps its original code and bindings. The registry never executes vault transactions and never holds authority over funds. New features ship as new deployments. Existing positions stay where they were created.

Registry contract

IvyVaultsRegistry is non-upgradeable and has an explicit nonzero administrator. Its public interface is small:

registerVersion(uint256 releaseId, address hub, bytes32 manifestHash)
setRecommendedVersion(uint256 releaseId)
hubOf(uint256 releaseId)
manifestHashOf(uint256 releaseId)
recommendedVersion()

Only the administrator can register a release or change the recommendation. The contract rejects zero release IDs, Hub addresses that are zero or have no code, empty manifest hashes, and any release ID or Hub address that is already registered. A registration can never be replaced or deleted. Recommending an unregistered release fails. A fresh registry has no recommendation, and registering a release does not recommend it. Registration and recommendation changes each emit an event. Reads of an unknown release revert. Registry authority and Hub authority are separate.

A release ID identifies a deployment. It is unrelated to IvyVaultsHub.version(), to EIP-712 domain versions and to deployment-manifest format versions. Registering code proves nothing about whether that code is immutable or audited. Verifying a release before registering it is the operator's job.

Deployment and evidence

The registry is deployed on its own. The Hub suite keeps its eight-contract order, manifest-v6 plans and recovery workflow, and the registry never takes a nonce inside a Hub sequence. Registry deployment has its own preparation, explicit execution and interruption-safe recovery.

Before preparing a registration, the tooling verifies the intended chain, the Hub deployment evidence, the runtime code and the module and library bindings against the saved artifacts and manifest. The verified release manifest is committed alongside its on-chain hash, and the artifacts and interfaces for older releases are preserved. An unsupported manifest or interface format fails loudly; nothing is ever encoded with the current build's ABI or signing rules on the assumption that an older release matches. Registration and recommendation are separate prepared operations, each simulated before explicit execution, like every other operator command.

Resolution and integration

A reusable release-resolution function turns a selected registry release into a concrete Hub address with verified matching artifacts, and operator transaction preparation uses it. The recommendation may serve as the default when creating a new vault. Anything that touches an existing position must name its release or its original Hub. It never follows the current recommendation implicitly.

Prepared transactions and typed signatures bind the selected Hub and chain, so a recommendation change after preparation cannot redirect them. A request that supplies both a Hub address and a registry release is rejected if they disagree. Explicit-Hub requests remain available for existing workflows and direct access. Token approvals resolve to the actual vault on that Hub. A position is identified by (chainId, hubAddress, vaultId), since local vault IDs can overlap across releases.

The transaction frontend lives outside this repository. What lives here is the resolution interface, examples and integration notes. The frontend uses the registry for discovery, keeps the concrete deployment identity in position URLs and state, and sends transactions straight to the resolved Hub. The documentation site does not contain a transaction router or a wallet application.

Coexistence and lifecycle guarantees

Changing the recommendation changes future default selection and nothing else. It does not update or pause a Hub, change a vault's owner or terms, migrate assets, invalidate bids, remove old claims or replace module bindings. Lifecycle, pause, fee, publisher and share-transfer controls keep working exactly as before. Operators keep the artifacts, indexing and support that older positions need.

An older Hub stays directly callable, including for new vault creation under its own admission rules. A registry recommendation is not an on-chain admission restriction. Live code cannot be patched. Settlement and consensual unwind on an old position are governed by its original deployment.

Validation

The tests work through public interfaces: the registry contract, deployment preparation and recovery, release resolution and operator preparation, and two independent Hub suites driven through their vault lifecycle. They cover unauthorized administration, permanent registrations, duplicate and invalid inputs, missing recommendations and unknown releases, chain, manifest, artifact and Hub mismatches, preserved explicit-Hub requests, unsupported release formats, registry deployment recovery, and transactions and signatures prepared before a recommendation change. One scenario deploys two Hub suites with overlapping vault IDs, registers and recommends the new release, then exercises, expires and claims the old positions and checks user balances and deployment bindings rather than registry state alone.
