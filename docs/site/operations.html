Operator runbook

This runbook covers deploying an immutable Hub suite and running individual vaults by hand. The CLI reads a JSON request, simulates the call, and prints either EIP-712 typed data or the calldata of a transaction. It never signs anything. Bids, reports and agreements are signed by wallets or multisigs from the printed typed data.

Before touching a live chain, run npm ci, npm run compile, npm run typecheck, npm run check:size and npm test -- --no-compile. You need Node.js 22.13.0 or newer and an RPC on a chain that supports the compiler's Osaka target, including transient storage. npm test -- --no-compile test/17-local-rehearsal.test.ts runs the whole procedure below on a throwaway local EVM and never touches your configured RPC or wallets. Run it first. It is the fastest way to see the sequence end to end.

Jump to token roles, unwind, premium treatment or platform fees.

Token roles and collateral

A vault deals with three token roles. The underlying is the asset the option is written on. The quote token measures the strike. The premium token is what the buyer pays. "Collateral" is not a fourth token; it is whichever of the first two the LPs deposit.

Product (strike 3,000 USDC per WETH) LP deposit / collateral Full physical exercise of 10 WETH
Covered call 10 WETH (underlying) Caller pays 30,000 USDC; recipient receives 10 WETH.
Cash-secured put 30,000 USDC (quote) Caller delivers 10 WETH; recipient receives 30,000 USDC.

Cash settlement pays intrinsic value in the collateral token, so WETH for this call and USDC for this put. The word "cash" does not mean a stablecoin payout. A call may list several quote/premium pairs before activation and the winning bid picks one. A put accepts exactly one pair, and its quote token must be the collateral. The premium token can share an address with the underlying or the quote, or be a third token. Even when addresses overlap, the vault keeps the premium, platform fee and buyer reserve budgets apart. Settlement proceeds join the residual pool that shareholders claim after reserves. Earned premium is claimed separately.

Requests and submission

Copy the example files, replace the placeholder addresses and timestamps, and write raw integer amounts as strings. A request normally has rpc, sender, hub, vaultId and the command's own fields. Never let an ID or amount become a JavaScript number; it will lose precision. USDC has six decimals, so 100 USDC is "100000000". Strike and spot are quote units per whole underlying. Premium is premium-token units per whole underlying.

npm run operator -- prepare-vault vault.json
npm run operator -- inspect-bid activation.json
npm run operator -- expire expiration.json

Without --send, every command only simulates and prints calldata. Read the chain, sender, destination, arguments and simulation result before going further. Chain state can move between your preflight and inclusion; the contracts recheck everything at execution. Any USD figure the CLI shows comes from the valuation you supplied. It cannot tell you whether that valuation is current.

Add --send only when you mean it. Submission goes through eth_sendTransaction with a signer the RPC exposes via eth_accounts, so the RPC has to know the sender. The CLI never loads private keys. For a hardware wallet or a Safe, take the printed transaction and submit it through that wallet's own flow. inspect-bid and the typed-* commands cannot send at all.

Deploy and recover

The Hub suite and the release registry are separate deployments with separate journals. The release registry guide covers the registry: deploying it, registering a verified suite, choosing a recommendation and resolving a release. Requests that name a hub directly keep working without the registry.

  1. Pick a dedicated deployer, a Hub administrator and an indicative report signer. In production the administrator should be a multisig. If the signer is a contract it must implement ERC-1271. A physical-only deployment needs no settlement publisher and no settlement methodology. Compile the exact build you intend to deploy, and use the same build if you resume.

  2. Fill deployment.json with RPC, deployer, admin and reportSigner. The defaults are an exerciseWindow of 3600 seconds and an auctionTimeout of 259200 seconds. Generate the plan with node directly so the redirected JSON has no npm banner in it:

    node scripts/operator.mjs prepare-deployment deployment.json > deployment-plan.json

  3. Inspect addresses, steps, chainId, genesisHash and the starting nonce. The order is fixed: IvyVaultRules, IvyOptionSettlement, IvyVault, IvyVaultsHub, IvyShares, IvyPremiums, IvyUnwind, IvyPriceFeed. The two libraries go first because the plan links their predicted addresses into the Hub bytecode and records every runtime link offset. Do not use the deployer for anything else while the sequence is running.

  4. Fill deployment-run.json with RPC, planFile and journalFile. Once the target network is approved, execute:

    node scripts/operator.mjs deploy deployment-run.json --send

  5. Keep the plan and the journal. If the run is interrupted, rerun the same command with the same files and the same build. The journal is written before each submission, again once the hash is known, and again after verified inclusion. On resume, each existing step must match on creation data, sender, nonce, receipt, runtime code and peer bindings, including every embedded library link. A lost submission hash is recovered by scanning chain history from the journal's start block. Nonce drift, evidence from the wrong chain, or an unknown or replaced pending transaction stops recovery. When that happens, investigate that transaction. Do not delete the journal and do not guess a new sequence.

Plans from earlier builds cannot be reused with this manifest-v6, eight-step build. Generate a fresh plan for any deployment that has not executed yet. An interrupted deployment has to be recovered with its original build and plan; swapping builds halfway is not supported.

The journal reports complete: true only after constructor bindings, library links and Hub administration all verify. At that point the administrator holds DEFAULT_ADMIN_ROLE and GUARDIAN_ROLE, nobody holds the settlement publisher role, and cashSettlementEnabled() is false. Before trading, grant BID_MASTER_ROLE to the auction operator and MARKET_MAKER_ROLE to each accepted buyer with grant-role requests naming role and account. The CLI hashes role strings, so manage DEFAULT_ADMIN_ROLE through its exact zero bytes32 using the contract ABI instead. There are no wiring, library replacement or upgrade transactions after deployment. Library calls run against Hub storage under the Hub's own authorization.

Prepare, fund and activate

  1. Check the token addresses, decimals and transfer behaviour, the owner's balance, the commitment size, the exact expiry and which option policies you will accept. For a physical launch use terms.allowedSettlement: 0 and terms.maxSettlementPriceAge: 0. For Cash or Either, confirm cashSettlementEnabled() first, then supply a positive terms.maxSettlementPriceAge and a settlementMethodology. The age limit cannot be changed by tightening. terms.priceFeed and terms.maxPriceAge configure the optional indicative activation check and are independent of settlement; any policy may leave the feed unset. The old settlementPriceFeed field no longer exists. Set terms.allowPartialExercise to an explicit boolean; it is fixed forever at creation. Vaults default to private deposits, so set terms.publicDeposits: true if you want pooling. The token list in the request is an operational allowlist for the CLI, not an on-chain whitelist.
  2. Set a positive minTradeUsdE6 that fits the product. The examples use an illustrative value, not a protocol minimum. Supply a reviewed collateral USD price and a market quote for every accepted quote token. prepare-vault checks the wallet balance against the minimum, sets minCollateral to the owner's prepared amount, and turns outOfTheMoneyBps into an absolute strike, rounded up for calls and down for puts. For a pooled vault this is the opening floor; the final supply may be larger. Work out the APR yourself from the agreed premium, the commitment value and the exact duration. The CLI does not price anything.
  3. Run prepare-vault, submit the createVault call, and read the vault ID and clone address from the receipt or the Hub getters. For each depositor, run approve-token for the collateral token and amount, then deposit with the same raw amount. Approvals target the clone, never the Hub. Calling vault.deposit(amount) directly is also fine and follows the same admission rules.
  4. The owner runs open-auction. If auctionStartsAt is nonzero, anyone may open it once that time passes. Read the auctionId and totalShares after opening; the bid commits to both. Deposits and withdrawals stop in Auction. Transfers still work if the admin has enabled them.
  5. If the vault uses an indicative feed, publish a fresh signed spot report before activation. Prepare typed-bid with the vaultId and the buyer's proposed fields. The tool reads the exact expiry, current auctionId, collateral amount and accepted pairHash from the chain; executor defaults to zero and recipient to the buyer. The buyer reviews all of it and signs under domain IvyVaultsHub, version 2, the chainId and the Hub address.
  6. The buyer approves the clone for the full premium, floor(premium × totalNotional / underlyingUnit). For a put, the notional is floor(collateral × underlyingUnit / strike). inspect-bid takes the real signature, the USD minimum and the collateral valuation, and simulates activation as the bid master. That checks the role, the signature, the policies, the oracle band and whether the premium is funded. Funding a later physical exercise is a separate obligation of whoever calls it.
  7. Submit activate with the same signed bid. LPs can claim-premium straight away. If transfers are enabled, a recipient of shares also receives the proportional unclaimed premium; premium already claimed stays where it is. File the signed bid and the activation receipt with the launch record.

A buyer can burn an unused nonce with cancelBid(nonce) through the ABI. A cancelled or reopened auction gets a new auctionId, so it needs a new typed bid even if nothing else changed.

Reports, exercise and expiration

Prepare report files outside the CLI and confirm the target Hub, or the indicative feed for signed spot reports, before submitting. Prices are raw quote-token units per whole underlying. For WETH/USDC, 2,500 USDC per WETH is 2500000000.

Indicative activation reports go through typed-report with kind: "spot". The domain is IvyPriceFeed, version 1, the chainId and the feed address. The feed's immutable signer signs; anyone may relay with publish-spot. Only spot reports exist on this path. Cash settlement uses the Hub commands below.

Exercise observations go through publish-settlement-exercise with hub, vaultId, settlementMethodology and report: { price, observedAt, validUntil }. This is a direct Hub call from the publisher, with no separate EIP-712 signature. The vault must be Live and cash-settled. The preview shows the underlying, selected quote and expiry the Hub derived from that vault. Timestamps must be positive, not in the future, and strictly later than the previous observation for that vault. When an American buyer exercises before expiry, the Hub checks the vault's fixed maximum age and the observation's validity deadline, both inclusive. A long validity deadline does not get around the age limit.

Expiry reports go through publish-settlement-expiry with hub, vaultId, settlementMethodology and report: { price, validUntil }. Publish for a Live cash vault at or after its expiry and no later than validUntil. A final price is write-once per vault. There is no administrator correction. Two vaults with the same pair and expiry still need separate transactions and may receive different prices. A vault settled late reads its finalized price indefinitely. For a late publication, submit the approved calculation for the original expiry with a current deadline. Check the derived pair, expiry, units and vault ID before sending.

Before cash goes live in production, approve a methodology that names the responsible operator, the sources, sampling, weighting, rounding, missing-data and outage rules, evidence retention and freshness settings. The expiry method is a 30-minute average ending at the vault's exact expiry. Exercise observations need an approved current-price calculation and validity policy of their own. Reference the methodology artifact through settlementMethodology in each vault's preparation and publication requests, and keep the evidence per vault. A shared method still means one publication per vault. Physical deployments need none of this. Neither the contracts nor the CLI verify sources or compute the average; the synthetic reports in the tests are rehearsal data only.

Enable cash after physical launch

The cash flag starts false. Prepare the methodology and the operator, then grant the publisher role with grant-settlement-publisher to a nonzero EOA or an authenticated helper. That grant does not enable anything by itself. The Hub admin then runs set-cash-settlement-enabled with hub, enabled: true and publisher. The CLI checks that the nominated address holds the role and previews the current and requested flag. The transaction itself carries only setCashSettlementEnabled(true). Confirm the flag before creating Cash or Either vaults.

The setter is admin-only and deliberately ignores role membership; a direct contract call skips the CLI's publisher check entirely. Keeping publication covered is the administrator's job. Granting, revoking or renouncing a role never moves the flag. If coverage is lost, disable new admissions if that is the right call and rotate authority. The preflight is a snapshot, not a promise that the publisher is online or will keep its role.

set-cash-settlement-enabled with enabled: false blocks new Cash and Either vaults and cash bid activation, including in auctions already open. Disabling needs no publisher. Physical bids still activate, including in existing Either vaults, and physical-only terms can never be loosened to cash. Existing cash positions keep publication, exercise, expiration, claims and agreed unwind while the flag is off. Revoking a publisher only stops that publisher's future reports; stored reports keep their rules. A missing report can only be filled by an authorized publisher. No flag change releases a reserve or erases an obligation.

EOA and optional contract publishers

The simple path is an EOA. Grant it the publisher role after deployment, enable cash, and have it submit publish-settlement-exercise and publish-settlement-expiry for each activated cash vault ID. There is no feed address to configure, no interface to implement and no helper to deploy. Each vault has its own stored reports even when pairs and expiries match.

A contract can hold the same role instead. It obtains or calculates the report under its own approved policy and calls the Hub's publication functions. The Hub only checks the caller's address; it never calls back into the helper to read a price. The helper must authenticate its upstream callers, because an open forwarding contract with the role would let anyone publish. The ExampleSettlementPublisher shows the shape: owner access control in front, the write-side interface behind. It demonstrates the trust boundary and nothing more. No production data source is implied.

Publisher rotation and incidents

DEFAULT_ADMIN_ROLE on the Hub controls SETTLEMENT_PRICE_PUBLISHER_ROLE. Use grant-settlement-publisher and revoke-settlement-publisher with hub and account. The role is checked when the publication executes. Any holder may publish for any eligible cash vault, and holding the role in several accounts creates no on-chain quorum. If you want a threshold, put it in a publisher multisig.

When a publisher becomes unavailable, grant a replacement and revoke the old one, then verify the Hub address and the resulting membership. Observations already published stay usable until their age or validity limit passes or a newer one replaces them. Finalized expiry prices survive forever. Revocation stops future publications and cannot undo a completed payment. A missing report keeps the buyer's obligation and the collateral locked until a valid report arrives or the parties agree an unwind. Admission pause does not block publication or existing-position management.

Check the calculation before publishing a final price. A wrong exercise observation can be superseded by a later verified one. A wrong final expiry price cannot be corrected by anyone. Record the incident and pause new affected admissions if appropriate. Do not promise a reversal of completed payouts, and do not substitute a current price for a missing historical report. If every Hub admin key is lost, publisher governance is lost with it. The pricing specification goes through these boundaries in detail.

For physical options the deadline is expiry + stateOf(vaultId).exerciseWindow. American holders can exercise from activation; European holders from expiry. Both must execute strictly before the deadline. The buyer or its current executor submits exercise with an underlying amount, and the caller funds and approves the clone: quote tokens for a call, underlying for a put. Everything goes to the configured recipient. Only the buyer can change the executor or recipient, with set-execution; a zero executor address revokes delegation.

American cash exercise before expiry uses the exercise observation, never the indicative feed. At or after expiry, both styles use the finalized report for the exact expiry, and a zero payout reverts. Cash expire prices the remaining notional and reserves the buyer's payout for claim-payout. Anyone may expire a physical option at or after its deadline and a cash option at or after expiry. Full exercise finalizes on the spot. Reaching a deadline does nothing by itself; someone has to send the transaction. Cash expiration also needs the finalized report.

After settlement, holders call claim with a share amount, which burns those shares for a proportional slice of the unreserved balances. Unpaid premium, premium dust, buyer payouts and refunds, and recoverable unwind contributions all stay reserved. claim-premium still works for holders with unpaid credit, even after burning every share. The buyer or executor calls claim-payout and the payment goes to the buyer's current recipient. To reconcile custody, read vault.reserved(token), vault.buyerReserved(token) and the premium module's claimable(vaultId, holder). The Hub's pendingPayout tracks only cash settlement in collateral, not unwind refunds.

If reports are unavailable, a cash vault stays Live and locked until a valid report or a unanimous unwind. A stale or missing feed never settles anything to zero. The admin can rotate publishers; nobody can correct a finalized price.

Admission pause and stalled auctions

A guardian uses pause with vaultId: "0" for global admission or a specific ID for one vault. Creation, deposits, opening and activation are blocked as applicable. Withdrawals, transfers, exercise, reports, settlement, claims and agreed unwinds continue, and no deadline moves.

The owner may cancel-auction immediately while admission is paused or once the expiry has passed. Otherwise the owner waits out the auction timeout snapshotted at creation. A bid master may cancel at any time. Cancellation returns the vault to Open and clears the schedule, after which holders can withdraw. A paused vault must be unpaused before it admits another deposit or auction, and an expired vault cannot reopen.

Premium treatment and emergency boundaries

Event Premium and fees Refund / continuation
Auction cancelled before activation Nothing collected. No premium refund; vault returns to Open.
Unwind consent revoked or proposal expired/replaced Earned LP premium and platform fees remain unchanged. Each LP can recover their contribution; the Live position continues under its normal deadlines.
Unwind executed Earned LP premium and platform fees are retained. Current LPs separately fund proportional contributions for the negotiated premium-token refund; buyer or executor claims it for the configured recipient.
Admission paused Earned premium, fee and claim entitlements are unchanged. Exercise, expiration, claims and agreed unwind continue; deadlines do not move.
Normal exercise or expiration Earned premium and fees remain retained and claimable. Settlement obligations are handled separately.

The policy is simple on purpose. Premium and fees are earned at activation, and any unwind refund is negotiated and funded on its own. An automatic refund out of premium would not work anyway: LPs may already have claimed theirs, so there is no guarantee the money is still in custody. Claiming premium does not excuse a current shareholder from a refund contribution. Refund funding sits in its own reserve in the vault and is never drawn from premium, fees or collateral.

The only emergency control is admission pause. A full execution freeze would be a separate product decision with its own specification covering permissions, affected actions, deadlines, resumption and outstanding payments. Admission pause is not that.

Prepare and execute a unanimous unwind

Only a Live vault can be unwound. The owner or the buyer calls propose-unwind with a future deadline and a refund in raw premium-token units; zero is allowed. typed-unwind returns the active agreement, with vaultId, nonce, deadline, exercisedNotional, supply and refund, under the EIP-712 domain bound to this chain and the unwind module.

Every current shareholder submits approve-unwind with that nonce. A holder can revoke-unwind later. A nonzero transfer to another holder invalidates both the sender's and the recipient's votes, and both must approve again at their new balances. Replacing the proposal increments the nonce and wipes all previous votes. None of this blocks ordinary exercise or settlement.

Each current LP approves the clone for premium tokens and calls fund-unwind with the nonce and an amount. The minimum is ceil(refund × current shares / proposal supply) in raw units, available as unwind.requiredContribution(vaultId, balance). Funding can happen before or after voting and can be topped up. One holder's overfunding never covers another's shortfall. Premium already claimed changes nothing here. If a token callback moves the funder's shares during funding, even away and straight back, the funding transaction reverts.

The buyer signs the exact active agreement. Anyone can then submit execute-unwind with vaultId, nonce and signature; the executing caller supplies no tokens. Execution checks the exercise and supply snapshot, unanimous consent from current holders and each approved holder's funding, then moves exactly the signed refund from the contribution reserve into a buyer reserve and finalizes the vault. No refund tokens leave the vault at that moment. Any exercise in between requires a fresh proposal, signature and approvals, and ordinary finalization makes the proposal unusable.

Before execution, a funder can call withdraw-unwind-contribution with the original nonce and get the whole deposit back. Withdrawing from the current proposal also revokes that holder's consent. Recovery stays available after revocation, replacement, deadline expiry, exercise, ordinary settlement and burning every share. Replacing a proposal does not roll old funds into the new nonce. Transfers keep each deposit attributed to its original funder.

After execution, anything above an approved holder's ceiling is still recoverable. Ceiling rounding can leave a surplus over the exact refund, which is shared out on recovery: each recovery gets floor(remaining surplus × holder ceiling / remaining total ceilings), then that holder's ceiling leaves the remaining weight. The last participant to recover takes whatever rounding dust is left. Three equal LPs refunding two raw units each fund one unit: the buyer receives two, the first two to recover get zero, the last gets one. So the dust depends on recovery order, but none of it is stranded. A zero-amount recovery still clears the participant's weight. Deposits from former holders who never approved are wholly recoverable and take no share of the surplus. Every recovery stays tied to the original wallet through later transfers or burns. To reconcile, read vault.unwindReserved(), unwind.contributions(vaultId, nonce, holder) and the completion state; the contribution getter reports the original deposit until recovery, which after execution is not the same as the recoverable amount.

The buyer or executor uses claim-payout for the refund, paid to the current recipient. Holders use ordinary claim for the remaining collateral and completed-exercise proceeds. Unpaid premium is still claimed separately. An unwind never claws it back.

Worked unwind scenarios

Zero refund. While Live, propose refund: "0" with a future deadline. Read typed-unwind, collect every holder's approve-unwind for that nonce and the buyer's signature, then execute. No token approval and no funding. Holders run claim and, if owed, claim-premium. There is no refund to claim.

Funded refund. With six-decimal USDC as premium token, propose refund: "100000000" for 100 USDC. With a 60/40 share split, the two LPs run approve-token with the clone as spender and fund-unwind for 60 and 40 USDC. After consent, signature and funding, anyone runs execute-unwind. The buyer or executor runs claim-payout; holders claim the residual pool and unpaid premium. Completed exercises stay completed.

Expired or replaced proposal. Nonce 1 cannot execute after its deadline. While still Live, the owner or buyer proposes again with a future deadline and gets nonce 2. Replacing a proposal that is still valid has the same effect. Read fresh typed data, get a new buyer signature and every current holder's approval. Nothing signed or approved for nonce 1 works for nonce 2. Revoking consent removes that holder's vote, not the option and not anyone's premium. Execution is allowed at the deadline itself, not after it.

Use the operator templates with the fields below. An unwind is an agreed close of a funded Live option. cancel-auction only returns a pre-activation auction to Open.

Platform fee and share-transfer administration

A fresh deployment starts with transfers disabled, a zero platform fee and the admin as treasury. DEFAULT_ADMIN_ROLE manages setTransfersEnabled(bool) and setPlatformTreasury(address). PLATFORM_FEE_MANAGER_ROLE manages setPlatformFeeBps(uint16); the admin holds that role initially and controls who else does. The rate can range from 0 to 10,000 bps, or 100%, because the fee is deducted from the gross premium.

Vault creation saves the current global rate in vaultPlatformFeeBps(vaultId). That exact rate is fixed for the vault: later global increases or decreases, including a change to or from zero, affect only subsequently created vaults. Cancelling and reopening an auction does not change the saved rate. Activation uses the saved rate and the current treasury, then records the applied rate, amount and recipient in platformFees(vaultId). Treasury changes affect future activations but never redirect an already allocated fee. Check the global rate before creating a vault and read its saved rate after creation. minPremium and Activated.totalPremium remain gross values.

The fee comes out of the premium token: floor(gross × rate / 10,000). At 200 bps, 1,000 USDC of gross premium sends 20 USDC to the treasury and 980 USDC to LPs. Do the arithmetic in raw integers. Rounding is down to the smallest premium unit, so any fractional fee unit stays with the LPs, who can claim their net share immediately. The vault reserves both allocations; platformFeeRemaining is independent of premiumRemaining and buyerReserved. Anyone can call the vault's claimPlatformFee() once to pay the snapshotted recipient. Changing the treasury later does not redirect fees already recorded, and a vault cannot be its own treasury. Fees stay earned through exercise, expiry and unwind. Unwind refunds are funded separately.

When transfers are enabled, a transfer moves floor(unclaimed × amount / pre-transfer balance) of the sender's premium credit, and a full transfer moves all of it. Claimed amounts never move. Duplicate IDs in a batch are aggregated before the proportional accounting. Burns preserve unpaid credit, including partial burns. Zero-amount and self transfers move no entitlement and do not invalidate unwind consent, but they still require transfers to be enabled.

Commands: set-platform-fee (rateBps), set-platform-treasury (recipient), set-transfers (enabled) and claim-platform-fee (vaultId). Each takes the usual hub and sender fields and simulates before building calldata. inspect-bid reports the gross premium, the saved vault rate as platformFeeBps, the platform fee and the net premium at that rate. Later global rate changes cannot alter this vault's fee calculation between preflight and execution. The treasury is selected at activation.
