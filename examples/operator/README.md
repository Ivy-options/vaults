# Operator request examples

These files are templates. Replace the uppercase address, timestamp and amount placeholders and the RPC URL before use. None of them contain keys. The [runbook](../../docs/site/operations.html) explains who may send each one and in what order.

- `deployment.json`: read-only `prepare-deployment` input. Save its output as `deployment-plan.json`. It predicts eight deployments: the two linked libraries first, then the vault implementation, Hub, modules and indicative feed. The result is physical-only, with `cashSettlementEnabled` false and no publisher. A `settlementMethodology` reference may be stored in the plan as metadata but is not required.
- `deployment-run.json`: explicit deployment or resume input. Keep its journal between attempts.
- `registry-deployment.json`: `prepare-registry-deployment` input for the separate release registry. Save the result as `registry-plan.json`. It does not touch the eight-contract Hub sequence.
- `registry-resume.json`: `deploy-registry` input naming that plan and its own recovery journal. Execution needs `--send`.
- `release-bundle.json`: `prepare-release-bundle` input naming a completed Hub plan and journal. Run it from that release's matching build and save the verified output as `release-1.json`.
- `registry-register.json`: `register-version` input naming the registry, release ID and saved bundle. Simulation verifies the deployment evidence and binds the bundle hash; submission needs `--send`.
- `registry-recommend.json`: `recommend-version` input. It selects an already registered release and does nothing to any Hub.
- `registry-claim.json`: `claim` through an explicitly selected registry release, with the position's local vault ID and share amount. The transaction still goes to the original Hub whatever the current recommendation.
- `vault.json`: private physical covered-call preparation, 10 WETH, 20% out of the money, with an illustrative $10,000 minimum. Review the token and price inputs for your chain.
- `cash-vault.json`: cash covered-call preparation for use after the publisher grant and feature activation. It carries the required methodology reference and a positive observation age.
- `bid.json`: `typed-bid` input. Copy its complete output `value` into an activation request's `bid` and collect the buyer signature. `activation.json` shows the envelope.
- `spot-report.json`: `IvyPriceFeed` `typed-report` input for activation checks. Add `signature` to relay it with `publish-spot`. Cash settlement uses the Hub publication requests below.
- `settlement-exercise.json`: `publish-settlement-exercise` input for a direct publisher transaction to `hub`. Its `validUntil` is enforced at exercise, alongside the vault's maximum observation age.
- `settlement-expiry.json`: `publish-settlement-expiry` input for the historical calculation at the exact expiry. Publication is irreversible.
- `settlement-role.json`: `grant-settlement-publisher` or `revoke-settlement-publisher` input, sent by the Hub admin. Role changes decide who may publish and never toggle cash availability.
- `cash-feature.json`: `set-cash-settlement-enabled` input. To enable, nominate an already authorized publisher for the CLI preflight; the transaction carries only the boolean. To disable during an outage, set `enabled: false` with no publisher.
- `transaction.json`: the common envelope. Add `amount` for deposit, withdraw, exercise and claim. Expire, claim-premium and claim-payout take no amount.
- `unwind-proposal.json`: owner or buyer proposal. After proposing, run `typed-unwind` with the common envelope, have the buyer sign its output, and collect each holder's `approve-unwind` with the returned nonce. `unwind-funding.json` is an LP's `fund-unwind` request after approving the clone for premium tokens; every current LP owes its proportional rounded-up contribution regardless of premium already claimed. `unwind-execution.json` is anyone's execution request once consent and funding are complete; the executing caller provides no tokens. `unwind-recovery.json` with `withdraw-unwind-contribution` recovers a deposit from a failed proposal or the excess after execution. The runbook covers ceiling-surplus recovery and what share transfers do to consent.

Capture JSON to disk with `node scripts/operator.mjs <command> file.json > prepared.json`. `npm run operator -- ...` also works, but npm prints a banner into stdout. Nothing is submitted unless you add `--send`.

The [release and integration guide](../../docs/site/releases.html) has the full registry workflow. For everyday operations, either add `registry`, `releaseId` and `releaseBundleFile` or keep an explicit `hub`; if both are present they must agree. Only `prepare-vault` may omit `releaseId` and take the recommendation. An existing position always keeps its original Hub and local vault ID, and because every CLI run prepares afresh, pin the release ID when repeating a request. This tooling supports bundle format 1, the `ivy-vaults-v2` interface and Hub manifest format 6.

`terms.allowPartialExercise` must be set explicitly in `vault.json`. False requires full exercise, true permits partial exercise, and the choice is locked before the first deposit.

To opt into cash, the Hub admin first prepares and submits `grant-settlement-publisher` with `settlement-role.json`, naming an EOA or an existing authenticated helper, then `set-cash-settlement-enabled` with `cash-feature.json`. Check `cashSettlementEnabled()` before using `cash-vault.json`. A cash vault needs a positive `terms.maxSettlementPriceAge`, fixed at creation, and a `settlementMethodology` reference. `priceFeed` and `maxPriceAge` only govern the optional activation check; a signed spot report there cannot stand in for a missing authoritative report. Before production cash admission, the referenced methodology must specify each pair's source, sampling, weighting, rounding, missing-sample and outage handling, observation validity, expiry calculation, responsible operator and evidence location. The tooling stores the reference and attests nothing about the source.

`test/17-local-rehearsal.test.ts` runs the whole sequence on a local EVM: deploy with no publisher, complete a physical exercise and LP claims, grant a publisher and enable cash, publish a synthetic exercise observation, attempt an expiration with the report missing, rotate the publisher and reject the revoked one, publish a late historical expiry report, expire permissionlessly and claim the buyer payout. Run it with `npx hardhat test test/17-local-rehearsal.test.ts` after compiling. The matching operational recovery is: grant the replacement with `settlement-role.json`, revoke the old publisher, prepare and verify `settlement-expiry.json` for the original expiry, publish it, then `expire` and `claim-payout` through `transaction.json` as the buyer. Each publication targets one Live cash vault by `vaultId`, and the Hub derives the pair and expiry itself, so vaults that share a pair and expiry still get separate publications.
