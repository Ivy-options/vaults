Releases and integration

Ivy ships new functionality as new immutable deployments rather than upgrades. IvyVaultsRegistry gives integrations one permanent address per chain to discover them. For each release it records a release ID, the release's Hub address and a hash of the release bundle, which is the deployment manifest plus its journal evidence and preserved artifacts. The registry administrator can recommend one release for new vaults. Registering and recommending are separate actions.

What remains fixed

A registration cannot be overwritten or removed. The registry cannot replace Hub code, rewire modules, call vault operations or move assets. Each vault stays bound to the Hub that created it, and its deposits, exercise, expiration, premium and residual claims follow that deployment. An older Hub stays directly usable under its own admission rules, new vault creation included. Changing the recommendation imposes no on-chain restriction on anything.

Release IDs identify deployments. They have nothing to do with the Hub's version() string, the EIP-712 domain version or the deployment-plan format version. Two releases can implement the same contract interface. A release ID only means something within one registry on one chain.

The registry does not validate source code or audit quality. Its administrator is responsible for what gets registered and recommended. The registration tooling verifies deployment evidence and bindings; reviewing the release's behaviour is a separate step that operators do before registering. The registry address itself is part of an integration's trusted configuration.

Immutability cuts both ways. A defect cannot be patched in place, so it may take a new release to fix it for future positions, while existing positions keep their original settlement and consensual-unwind rules. The registry adds no emergency withdrawal and no forced migration. Admission pauses, role management, transfer controls, fees and optional cash-price publication remain the administrative powers each Hub already defines.

Deploy the registry once

Use the same Node and compiler setup as the Hub deployment runbook and run commands from the repository root. Choose the registry administrator independently of the Hub administrator; the registry holds no Hub role.

Prepare a request with rpc, deployer and admin, then save the predicted deployment:

node scripts/operator.mjs prepare-registry-deployment registry-deployment.json > registry-plan.json

Inspect the chain, administrator, nonce, creation data and registry address. Prepare registry-run.json with rpc, planFile: "registry-plan.json" and journalFile: "registry-journal.json", then execute:

node scripts/operator.mjs deploy-registry registry-run.json --send

Keep the plan and the journal. To resume after an interruption, use the same command, files and registry artifact. Recovery verifies the creation evidence before adopting existing code and never creates a second registry. The registry has its own one-contract plan. If it shares a deployer with a Hub suite, finish it before preparing the Hub plan, and never let it consume a nonce from an already prepared eight-contract sequence.

Register and recommend a release

Deploy a Hub suite with its normal manifest-v6 plan and recovery journal. The registry changes nothing about that plan, the seven-argument Hub constructor or the physical-only starting state.

Prepare a bundle request with rpc, planFile and journalFile for the completed Hub deployment. From the checkout that has that release's matching artifacts, run:

node scripts/operator.mjs prepare-release-bundle release-bundle-request.json > release-bundle.json

The bundle has format: 1, interfaceFormat: "ivy-vaults-v2", manifest, journal and artifacts, so the contract interfaces and deployment evidence travel with the release. The verifier rebuilds the manifest from the artifacts, checks the chain and creation receipts, and checks runtime history and immutable module and library bindings. The RPC has to serve the historical code and receipts those checks read. Archive the bundle and the original build. They are part of the release, not temporary output.

Prepare register-release.json with rpc, sender (the registry administrator), registry, releaseId and releaseBundleFile: "release-bundle.json". The file path resolves from the command's working directory. Registration hashes the bundle to produce manifestHashOf(releaseId), so the hash commits to the artifacts and evidence as well as the manifest. Do not edit the bundle after registration.

node scripts/operator.mjs register-version register-release.json
node scripts/operator.mjs register-version register-release.json --send

The first command verifies the bundle, simulates the registration and prints the transaction for review. The second submits it. Verify the registered Hub and hash before recommending. A recommendation is its own request with rpc, sender, registry and releaseId:

node scripts/operator.mjs recommend-version recommend-release.json
node scripts/operator.mjs recommend-version recommend-release.json --send

Only registered releases can be recommended. Registration by itself leaves the recommendation alone, and a new registry has none. A registration cannot be edited to fix a mistake; a corrected deployment gets a new release ID. Recommendation changes never pause, upgrade or migrate a Hub.

Prepare transactions for a selected release

Operator requests may keep naming hub directly. To go through the registry instead, supply registry, releaseId and releaseBundleFile alongside the command's usual sender, vault and token fields. If hub is also present it must match the registration. The output is still a transaction addressed to the resolved Hub, or to the actual vault or token the operation targets.

Only prepare-vault may omit releaseId and take the current recommendation, with its matching bundle. Commands for an existing vault must name the release or use the original explicit Hub. They never pick a Hub from the moving recommendation. Missing, incompatible or mismatched release evidence fails before any calldata is encoded. A release's signing-domain version is verified separately from its registry release ID.

After preparing, keep the returned chain, destination and calldata, or the full typed-signature payload, and send that through the wallet rather than preparing again against a newer recommendation. Every CLI invocation prepares afresh against the state at that moment, including with --send, so pass the releaseId explicitly when repeating a command.

This build supports bundle format 1, Hub deployment manifests in format 6 and the ivy-vaults-v2 interface. A future incompatible interface needs its own reviewed tooling adapter and is rejected by this build rather than interpreted through the current ABI. Rotating an administrative role does not change immutable release bindings, and existing positions stay usable through their original Hub.

Frontend integration

The transaction frontend is maintained outside this repository. The reusable resolver and the operator transaction builder show the contract it should follow:

  1. Configure a registry address per supported chain. Resolve the recommended release only when starting a new position, or let the user pick a registered release explicitly.
  2. Load and verify that release's manifest and matching artifacts. An unknown interface format must produce an unsupported-release error, never a fallback to another release's ABI or signing rules.
  3. Show the selected Hub and release before the user commits, and prepare the transaction for that concrete Hub address. A later recommendation change cannot redirect a transaction that is already prepared.
  4. Store positions and index events by (chainId, hubAddress, vaultId), and keep that identity in position URLs, local state and backend records. Read LP balances from the release's share-token address with its local token ID.
  5. Return to that exact Hub for an existing position. Never resolve the current recommendation to decide where an old vault's deposit, exercise or claim belongs. Token approvals target that vault's actual clone.
  6. Keep older artifacts and interfaces available, with their operational support. Users must retain direct contract access whether or not a release is recommended in the UI.

The registry is for discovery. Wallet transactions and signature verification stay bound to the selected deployment. There is no forwarding, no shared Hub storage and no transaction router.

resolveRelease, exported from scripts/releases.mjs, has no filesystem dependency. It takes an ethers JSON-RPC-capable provider such as JsonRpcProvider or BrowserProvider, a request containing the parsed releaseBundle, the supported artifacts, and an optional { allowRecommended: true } for new-position discovery. The provider must support send(method, params) plus historical code and receipt reads. Runtime verification reads code with an uncached eth_getCode so that an empty read from before deployment cannot invalidate a freshly mined one, and recovery reads the latest block height without the provider cache when scanning for a hash lost during an interruption. It returns the concrete Hub, chain, registry, release ID, bundle hash and saved artifacts. Browser integrations load the JSON bundle themselves; the CLI also accepts releaseBundleFile. Use the returned saved interfaces for contract calls and keep the Hub address when indexing the creation receipt.

Finding vault creation in the source

The user calls createVault(terms, pairs) on the Hub address. The implementation, state declarations and shared guards live together in contracts/IvyVaultsHub.sol. The separate custody, share, premium and unwind contracts retain their accounting responsibilities.

That function increments the local vault counter, calls Clones.clone(vaultImplementation) and initializes the new clone with the Hub address, vault ID, collateral and premium module in the same transaction. The implementation is deployed once per Hub suite; every clone has its own address and storage. The registry plays no part in this path.

See the registry specification, the operator runbook and the request examples.
